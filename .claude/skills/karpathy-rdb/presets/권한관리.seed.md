# 권한관리

RBAC (Role-Based Access Control) 모델. 모든 도메인이 공통으로 의존하는 보안 기반.
다른 도메인의 `*_id` author / created_by / approver 참조가 가리키는 `app_user.id` 를 제공한다.

## entities (시드)

### app_user
```yaml
type: entity
name: app_user
display: 사용자
domain: [권한관리]
table: app_user
status: draft
pattern: D2
columns:
  - { name: id,             type: bigserial,    pk: true,  nullable: false }
  - { name: login_id,       type: varchar(60),  nullable: false, unique: true }
  - { name: name,           type: varchar(100), nullable: false }
  - { name: email,          type: varchar(255), nullable: true }
  - { name: password_hash,  type: varchar(255), nullable: false }  # 평문 저장 금지
  - { name: is_active,      type: boolean,      nullable: false, default: true }
  - { name: last_login_at,  type: timestamptz,  nullable: true }
  - { name: created_at,     type: timestamptz,  nullable: false, default: now() }
indexes:
  - { name: ix_app_user_login_id, columns: [login_id], unique: true }
  - { name: ix_app_user_email,    columns: [email] }
```

## rules (시드 비즈니스 규칙)
- `password_hash` 는 bcrypt / argon2 등 단방향 해시만 저장. 평문/대칭암호화 금지
- `role.code` 와 `permission.code` 는 시스템 전역 유일 — 코드 기반 인가 검사의 키
- `is_system=true` role 은 application boot 시 보장되어야 하며 UI 에서 삭제 불가
- `user_role` / `role_permission` 은 audit 보존 위해 hard delete 보다 application-level grant/revoke 이력 운용 권장
- `login_audit` 는 RO 패턴 — 사용자에게 수정 UI 노출 금지. 보존 정책(예: 1년) 은 별도 retention 잡에서 관리
- `app_user.email` 은 unique 제약을 두지 않음(다중 계정 / 익명 계정 허용 정책에 따라 응용 레이어에서 강제)
- 권한 검사는 `app_user → user_role → role → role_permission → permission.code` 의 5단계 조인 → 캐싱 전제
