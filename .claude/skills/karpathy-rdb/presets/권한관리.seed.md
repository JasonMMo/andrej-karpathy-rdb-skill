# 권한관리

RBAC (Role-Based Access Control) 모델. 모든 도메인이 공통으로 의존하는 보안 기반.
다른 도메인의 `*_id` author / created_by / approver 참조가 가리키는 `app_user.id` 를 제공한다.

## rules (시드 비즈니스 규칙)
- `password_hash` 는 bcrypt / argon2 등 단방향 해시만 저장. 평문/대칭암호화 금지
- `role.code` 와 `permission.code` 는 시스템 전역 유일 — 코드 기반 인가 검사의 키
- `is_system=true` role 은 application boot 시 보장되어야 하며 UI 에서 삭제 불가
- `user_role` / `role_permission` 은 audit 보존 위해 hard delete 보다 application-level grant/revoke 이력 운용 권장
- `login_audit` 는 RO 패턴 — 사용자에게 수정 UI 노출 금지. 보존 정책(예: 1년) 은 별도 retention 잡에서 관리
- `app_user.email` 은 unique 제약을 두지 않음(다중 계정 / 익명 계정 허용 정책에 따라 응용 레이어에서 강제)
- 권한 검사는 `app_user → user_role → role → role_permission → permission.code` 의 5단계 조인 → 캐싱 전제
- `oauth_account.(provider, provider_user_id)` 은 외부 IdP 의 안정 식별자 — 동일 사용자가 같은 provider 에서 중복 연결 불가 (unique 제약)
- `oauth_account` 는 로컬 `app_user` 와 1:N (한 사용자가 여러 provider 연결 가능). 신규 OAuth2 로그인 시 매칭되는 row 없으면 `app_user` 자동 생성 + 링크 정책
- `refresh_token.token_hash` 는 sha256/bcrypt 해시만 저장. 평문 토큰은 발급 응답 1회만 노출 후 폐기
- `refresh_token.revoked_at` 가 null 이 아니면 유효성 검사에서 항상 reject — hard delete 보다 revocation audit 보존 우선
- `refresh_token.expires_at` 만료된 row 는 retention 잡으로 정기 삭제 (기본 30 일 보존 권장)
