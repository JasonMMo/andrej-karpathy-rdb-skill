# 공급망

SCM (Supply Chain Management) — 발주(purchase) → 입고(goods receipt) 흐름.
공급업체(supplier)와 그 담당자를 관리하고, 발주서를 작성·확정한 뒤 입고
시점에 재고관리·창고에 물량을 흘려보낸다.

기존 도메인과의 연계:
- 재고관리(sku, warehouse): purchase_order_item·goods_receipt_item이 sku에 FK,
  purchase_order·goods_receipt가 warehouse에 FK (입고 창고)
- 권한관리(app_user): requester_user_id로 발주 요청자 RBAC와 직결
- 주문관리는 판매 측, 공급망은 구매 측 — 직접 FK 없음 (서비스 계층에서 연계)

### purchase_order
```yaml
type: entity
name: purchase_order
display: 발주서
domain: [공급망]
table: purchase_order
status: draft
pattern: MD  # master-detail — 발주서 헤더 + purchase_order_item 자식 그리드
columns:
  - { name: id,                  type: bigserial,    pk: true,  nullable: false }
  - { name: po_number,           type: varchar(30),  nullable: false, unique: true }
  - { name: supplier_id,         type: bigint,       nullable: false }
  - { name: requester_user_id,   type: bigint,       nullable: false }  # → 권한관리.app_user
  - { name: deliver_warehouse_id, type: bigint,      nullable: false }  # → 재고관리.warehouse
  - { name: status,              type: varchar(20),  nullable: false, default: 'draft' }
  - { name: total_amount,        type: "numeric(14,2)", nullable: false, default: 0 }
  - { name: currency,            type: varchar(10),  nullable: false, default: 'KRW' }
  - { name: ordered_at,          type: timestamptz,  nullable: true }
  - { name: expected_arrival_at, type: date,         nullable: true }
  - { name: closed_at,           type: timestamptz,  nullable: true }
  - { name: note,                type: text,         nullable: true }
  - { name: created_at,          type: timestamptz,  nullable: false, default: now() }
indexes:
  - { name: ix_po_number,    columns: [po_number], unique: true }
  - { name: ix_po_supplier,  columns: [supplier_id] }
  - { name: ix_po_requester, columns: [requester_user_id] }
  - { name: ix_po_warehouse, columns: [deliver_warehouse_id] }
  - { name: ix_po_status,    columns: [status] }
workflow:
  status_column: status
  states: [draft, confirmed, partially_received, received, closed, cancelled]
  transitions:
    - { action: confirm,        from: [draft],                            to: confirmed }
    - { action: partial_receive, from: [confirmed, partially_received],   to: partially_received }
    - { action: receive,        from: [confirmed, partially_received],    to: received }
    - { action: close,          from: [received],                         to: closed }
    - { action: cancel,         from: [draft, confirmed],                 to: cancelled }
```

## rules (시드 비즈니스 규칙)

- supplier.code, purchase_order.po_number, goods_receipt.gr_number는 시스템 내 유일
- purchase_order.status enum: `draft|confirmed|partially_received|received|closed|cancelled`.
  workflow 가드로 전이 강제
- draft 상태에서만 purchase_order_item을 자유롭게 수정 가능. confirmed 이후는
  사실상 readonly (서비스 계층 가드)
- purchase_order.total_amount = SUM(items.ordered_quantity * items.unit_price).
  item 변경 시 헤더 재계산 (서비스 책임)
- goods_receipt는 INSERT-only (RO 패턴). UPDATE/DELETE 금지
- 입고 시 goods_receipt_item INSERT → 같은 트랜잭션에서:
  (a) purchase_order_item.received_quantity 누적,
  (b) 모든 item이 충족되면 purchase_order.status를 received로 자동 전이,
  (c) 재고관리.stock 테이블에 inbound 이동 기록 (cross-domain orchestration)
- requester_user_id, received_by_user_id는 권한관리.app_user.id 참조 —
  RBAC로 본인 요청 발주만 수정/취소 가능하도록 service guard 적용 (Stage 3)
- sku_id, warehouse_id는 재고관리 도메인 cross-domain FK — combined wiki에서는
  실제 FK 제약, 단독 wiki에서는 plain bigint 컬럼으로 유지 (Growth-21b-4 메커니즘)
- on_delete 정책: supplier 삭제 시 contacts cascade, supplier가 발주 이력 있으면
  restrict (purchase_order.supplier_id가 막음)
